# API-справочник Эвектио

Полная спецификация в формате OpenAPI доступна на запущенном сервисе по адресу `GET /docs` (Swagger UI) и `GET /openapi.json` (машиночитаемая схема). Этот документ — то же самое, но в виде текста, для сдачи вне запущенного стенда: назначение каждого метода, тело запроса/ответа и примеры `curl`.

Базовый адрес по умолчанию — `http://localhost:8000`. Аутентификация не требуется: сервис предназначен для развёртывания в закрытом контуре медицинской организации, публикация в недоверенной сети — только за reverse proxy с TLS и аутентификацией (см. `docs/DEPLOYMENT.md`).

## Обзор методов

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Готовность сервиса, версия модели |
| `GET` | `/v1/model` | Поддерживаемые области, типы нарушений, пороги, калибровка пикселя |
| `POST` | `/v1/analyze` | Пакетная обработка «как в ТЗ»: вход — файлы, выход — ZIP-архив отчёта |
| `POST` | `/v1/jobs` | Обработка для веб-интерфейса: JSON с результатами и ссылками |
| `GET` | `/v1/jobs/{id}/preview/{i}` | PNG-визуализация одного снимка (карта вклада, ось, разметка) |
| `GET` | `/v1/jobs/{id}/image/{i}` | Исходное изображение без наложений |
| `GET` | `/v1/jobs/{id}/overlay/{i}` | Визуализация, обрезанная по кадру исходного изображения |
| `GET` | `/v1/jobs/{id}/download` | ZIP со всеми результатами задачи |
| `GET` | `/v1/jobs/{id}/case/{i}/zip` | ZIP одного исследования из очереди |
| `GET` | `/v1/jobs/{id}/zip` | ZIP отмеченных исследований (или всех — без параметра) |
| `POST` | `/v1/jobs/{id}/review/{i}` | Подтверждение/отклонение вывода и разметки специалистом (ТЗ 2.6) |

Далее — по каждому методу.

## `GET /health`

Проверка готовности (liveness/readiness), используется Docker `HEALTHCHECK` и балансировщиком.

**Ответ `200`:**

```json
{
  "status": "ok",
  "service": "evectio",
  "version": "1.5.0",
  "model_version": "dxa-quality-criteria-4.0"
}
```

```bash
curl -f http://localhost:8000/health
```

## `GET /v1/model`

**Ответ `200`:**

## `POST /v1/analyze`

Основной пакетный метод в духе ТЗ: вход — файлы, выход — готовый ZIP-архив отчёта. Без сохранения состояния на сервере между запросами.

**Запрос:** `multipart/form-data`, поле `files` (можно указать несколько раз) — DICOM-файлы (`.dcm`, `.dicom` или без расширения — распознаются по сигнатуре `DICM`) и/или `.zip` с DICOM внутри. Другой формат отклоняется с `415`.

`path_to_study` в результатах повторяет то, что было загружено: при одном ZIP — путь внутри архива (`study-1/series-2/IM000001`), при нескольких загрузках — `имя_архива/путь` для ZIP и исходное имя для отдельных файлов. Кириллические имена в ZIP без UTF-8-флага (Windows, консольный `zip`) декодируются корректно.

**Ответ `200`:** `application/zip` — тот же набор файлов, что и `GET /v1/jobs/{id}/download` (см. ниже). Заголовок `X-DXA-Summary` дублирует сводку в JSON:

```json
{"files":3,"success":3,"failure":0,"with_violations":1,"manual_review":2}
```

```bash
curl -f -X POST http://localhost:8000/v1/analyze \
  -F 'files=@study.zip;type=application/zip' \
  --output evectio-results.zip
```

**Ошибки:** `400` — файлы не переданы, ZIP повреждён, в загрузке нет ни одного DICOM или архив небезопасен (Zip Slip, превышение лимита файлов/объёма); `413` — файл больше 1 ГБ; `415` — файл не DICOM и не ZIP. Временные файлы запроса при ошибке удаляются.

Обработка идёт в отдельном потоке: во время большого пакета сервис продолжает отвечать на `GET /health` и запросы веб-интерфейса.

## `POST /v1/jobs`

Тот же анализ, но результат — JSON с данными для интерфейса, а исследование остаётся на сервере (в памяти процесса, файлы во временном каталоге) в течение `expires_in_seconds` (1 час, не более 32 задач одновременно — старые вытесняются). Именно этот метод вызывает веб-страница при загрузке снимков.

**Запрос:** тот же `multipart/form-data` с полем `files`, что и `/v1/analyze`.

**Ответ `200`:**

```json
{
  "job_id": "3f2a1c9e...",
  "expires_in_seconds": 3600,
  "summary": {"files": 2, "success": 2, "failure": 0, "with_violations": 1, "manual_review": 1},
  "results": [
    {
      "path_to_study": "study.dcm",
      "anatomical_region": "Поясничный отдел позвоночника",
      "projection": "Прямая (AP)",
      "projection_code": "AP",
      "projection_source": "dicom:PatientOrientation",
      "quality_class": 1,
      "quality_prob": 0.681,
      "violations": [{"title": "Присутствуют посторонние предметы", "description": "..."}],
      "markup": {"shapes": ["..."], "checks": ["..."], "status": "proposed"},
      "measurements": {"axis_angle_deg": -0.6},
      "recommendations": ["..."],
      "review": {},
      "preview_url": "/v1/jobs/3f2a1c9e.../preview/0",
      "overlay_url": "/v1/jobs/3f2a1c9e.../overlay/0"
    }
  ],
  "download_url": "/v1/jobs/3f2a1c9e.../download"
}
```

Полный список полей одного результата — тот же набор, что уходит в `manifest.json` (см. `README.md`, раздел «Выходные данные»), плюс `preview_url`/`overlay_url` (`null`, если визуализация не построена).

**Ошибки:** те же коды, что у `/v1/analyze`.

## `GET /v1/jobs/{job_id}/preview/{result_index}`

PNG заданного снимка из задачи: тепловая карта вклада признаков, измеренная ось (для позвоночника) и статус-бар с вердиктом — то, что показывается во вкладке «С ИИ».

**Ответ:** `200 image/png`, либо `404`, если задача истекла или визуализация не была построена (например, при ошибке чтения DICOM).

## `GET /v1/jobs/{job_id}/image/{result_index}`

То же изображение, но без каких-либо наложений — источник для вкладки «Снимок» и для редактора разметки на странице. Кадр приведён к физическому соотношению сторон (с учётом размера пикселя: PixelSpacing из файла, при его отсутствии — 1,05 × 0,60 мм), поэтому по размеру совпадает с `overlay`.

**Ответ:** `200 image/png`, либо `404` (задача истекла или исходный файл вне каталога задачи).

## `GET /v1/jobs/{job_id}/overlay/{result_index}`

Визуализация из `preview`, обрезанная строго по кадру исходного изображения — используется во вкладке «С ИИ», чтобы переключение между вкладками не двигало картинку.

**Ответ:** `200 image/png`, либо `404`.

## `GET /v1/jobs/{job_id}/download`

ZIP со всеми результатами задачи целиком: `results.csv`, `results.xlsx`, `manifest.json`, `visualizations/*.png`, `dicom_sr/*.dcm`, `dicom_markup/*.dcm`, `dicom_viz/*.dcm`. Тот же архив, что вернул бы `/v1/analyze` для того же входа. Пересобирается заново после каждого `POST .../review/{i}`, поэтому всегда отражает актуальные решения специалиста.

```bash
curl -f http://localhost:8000/v1/jobs/$JOB_ID/download --output results.zip
```

**Ответ:** `200 application/zip`, либо `404` (задача не найдена/истекла).

## `GET /v1/jobs/{job_id}/case/{result_index}/zip`

ZIP одного исследования из очереди — кнопка «Скачать ZIP» во вьюере конкретного снимка. Содержит только то, что относится к этому снимку: исходный DICOM (`dicom/…`), его визуализацию (`visualizations/…`), DICOM SR (`dicom_sr/…`) и разметку (`dicom_markup/…`, если построена), плюс `case.json` — тот же объект, что и элемент `results` в ответе `/v1/jobs`. Имя файла — `{номер}_{имя исследования}.zip`.

```bash
curl -f "http://localhost:8000/v1/jobs/$JOB_ID/case/0/zip" --output case-0.zip
```

**Ответ:** `200 application/zip`; `404` — задача или снимок не найдены; `409` — снимок обработан с ошибкой, архива для него нет.

## `GET /v1/jobs/{job_id}/zip`

ZIP по выбору: несколько исследований, отмеченных в очереди просмотра чекбоксами. Каждое — в собственной пронумерованной папке (`{номер}_{имя}/…`), внутри та же структура, что у ZIP одного исследования. Без параметра `indices` (или если он пустой) возвращает то же, что `/v1/jobs/{id}/download` — весь архив задачи, поэтому кнопка «Все ZIP» в очереди ссылается прямо сюда.

**Параметр запроса:** `indices` — номера результатов через запятую, `0`-based (`?indices=0,2,5`).

```bash
curl -f "http://localhost:8000/v1/jobs/$JOB_ID/zip?indices=0,2" --output selected.zip
curl -f "http://localhost:8000/v1/jobs/$JOB_ID/zip" --output all.zip   # эквивалент /download
```

**Ответ:** `200 application/zip`; `400` — в `indices` есть нечисловой или несуществующий номер; `404` — задача не найдена/истекла.

## `POST /v1/jobs/{job_id}/review/{result_index}`

ТЗ 2.6: специалист подтверждает или отклоняет вывод модели и, отдельно, автоматическую разметку. После сохранения `manifest.json` и ZIP задачи пересобираются, DICOM SR получает `VerificationFlag=VERIFIED` с `VerifyingObserverSequence`, а `dicom_markup/*.dcm` переписывается (при `edited`) или удаляется (при `rejected`).

**Тело запроса** (`application/json`):

```json
{
  "decision": "confirmed",
  "reviewer": "Иванова А.А.",
  "comment": "Согласна с выводом",
  "organization": "",
  "markup_decision": "edited",
  "markup_shapes": [
    {"label": "L2/L3", "points": [[118.0, 152.0], [182.0, 150.0]]}
  ]
}
```

| Поле | Тип | Обязательное | Значения |
|---|---|---|---|
| `decision` | строка | да | `confirmed` — согласен с выводом модели, `rejected` — не согласен |
| `reviewer` | строка (1–64) | да | ФИО или идентификатор специалиста |
| `comment` | строка (≤1000) | нет | Комментарий специалиста |
| `organization` | строка (≤64) | нет | Организация, если требуется в SR |
| `markup_decision` | строка | нет, по умолчанию `accepted` | `accepted` — автоматическая разметка верна; `edited` — верна с учётом правок в `markup_shapes`; `rejected` — разметка неверна и удаляется |
| `markup_shapes` | массив | нужен только при `edited` | До 16 элементов `{label, points}}`; `label` — как в автоматической разметке (`L1/L2`, `Область интереса бедра` и т.д.), `points` — координаты в пикселях исходного изображения |

**Ответ `200`:**

```json
{"status": "ok", "result": { "...": "обновлённый результат этого снимка, включая поле review" }}
```

`result.review` после сохранения:

```json
{
  "decision": "confirmed",
  "reviewer": "Иванова А.А.",
  "organization": "",
  "comment": "Согласна с выводом",
  "reviewed_at": "2026-09-24T15:02:11+03:00",
  "model_quality_class": 1,
  "markup_decision": "edited"
}
```

```bash
curl -f -X POST http://localhost:8000/v1/jobs/$JOB_ID/review/0 \
  -H 'Content-Type: application/json' \
  -d '{"decision":"confirmed","reviewer":"Иванова А.А.","markup_decision":"accepted"}'
```

**Ошибки:** `404` — задача или снимок не найдены; `409` — исходный DICOM недоступен для подтверждения (задача истекла); `422` — `decision`/`markup_decision` вне допустимых значений, `reviewer` пуст, или разметки для правки не существует.

## Ограничения и защита загрузки

- до 1 ГБ на файл (`413` при превышении);
- ZIP-архив на входе — не более 10 000 объектов и 5 ГБ в распакованном виде;
- защита от Zip Slip: путь каждого элемента архива проверяется, чтобы остаться внутри каталога распаковки;
- задача (`job_id`) живёт 1 час и не более 32 одновременно — старые вытесняются новыми;
- все ошибки обработки одного файла внутри пакета не прерывают остальные — файл получает `processing_status: "Failure"` и попадает в отчёт с этим статусом, а не приводит к ошибке всего запроса.

## Коды ошибок

| Код | Когда |
|---|---|
| `400` | Файлы не переданы; повреждённый, небезопасный или слишком большой ZIP; в загрузке нет DICOM; неверный параметр (`indices`) |
| `404` | Задача (`job_id`), снимок (`result_index`) или файл превью не найдены |
| `409` | Исходный файл задачи недоступен (например, ZIP одного исследования для файла с ошибкой обработки) |
| `413` | Загружаемый файл больше 1 ГБ |
| `415` | Файл не является DICOM (по расширению или сигнатуре `DICM`) и не является ZIP |
| `422` | Тело `POST .../review/{i}` не прошло валидацию |
| `500` | Контролируемая внутренняя ошибка — тело ответа `{"status": "Failure", "error": "..."}` |
